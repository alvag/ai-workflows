Reporte — punto de despacho "Delegación a `sdd-flow` (prompt del subagente)"
(sección de skills/sdd-pr-feedback/reference.md, consumida desde el Paso 5 de
skills/sdd-pr-feedback/SKILL.md). Corrida en solo lectura: no ejecuté el encargo.

1) QUÉ ENCARGO DESCRIBE

Es el prompt congelado del subagente de implementación del Paso 5 de `sdd-pr-feedback`: el
único tramo del flujo de feedback de PR que se delega. El encargo para el agente que lo recibe
es correr la **Vía B completa de `sdd-flow`** ("implement .plans/<id>/") sobre un flujo ya
preparado por el conductor, dentro de un solo repo y parado sobre la rama del PR.

Concretamente: leer skills/sdd-flow/SKILL.md (y su reference.md si hace falta) y seguir ese
contrato al pie de la letra — leer plan/spec/tasks de .plans/<id>/, implementar los cambios,
correr el `verify` de los AC más tests/build, y actualizar en .plans/<id>/ solo lo que la Vía B
manda (marcas [x], `status`, sección `## Verify`).

No es el subagente-por-task de `sdd-flow`: es la Vía B entera en un despacho, con el reporte del
agente delegado de `sdd-orchestrator`. Restricciones duras del encargo:
- `cross_review.mode: off` como override de la corrida (el conductor ya cross-revisó spec y
  plan/tasks; además la Vía A de cross-review despacha otro subagente y anidar no es confiable).
- Frenar antes de commitear: nada de git add/commit/push, nada fuera del repo.
- No tocar .specify/ ni otros flujos de .plans/.
- Sin usuario delante: no hacer los checkpoints conversacionales de la Vía B; implementación
  inline salvo que el entorno permita despachar subagentes propios. Bloqueo real → STATUS: failed.
- No crear ramas: ya se está sobre la rama del PR indicada por el `branch` del header.

Mecanismo de despacho según el conductor (tabla de la misma sección): Claude Code → subagente del
entorno (Agent/Task), un despacho; Codex CLI → `codex exec -s workspace-write -C <repo>
--skip-git-repo-check --output-last-message <out.txt> - < <prompt.txt>` (prompt por archivo,
nunca inline); sin subagentes → el conductor implementa inline como degradación.

2) QUÉ ENTRADA NECESITARÍA PARA EJECUTARLO

Del prompt mismo (placeholders a resolver antes de despachar):
- La ruta del repo de trabajo, con todo comando y ruta relativos a él.
- La ruta del directorio de skills donde vive sdd-flow/SKILL.md (accesible y legible).
- El `<id>` del flujo, para ubicar .plans/<id>/.

Del estado en disco (lo que el conductor "prepara antes de despachar"):
- .plans/<id>/ con spec.md, plan.md y tasks.md ya aprobados y cross-revisados en los Pasos 3 y 4.
- El header YAML obligatorio en plan.md: `id`, `branch` (la rama del PR, no una nueva),
  `base_commit` (SHA base del PR), `change_type`, `complexity`, `created_at` y sobre todo
  `status: tasks-ready` — sin ese status el `resume` de la Vía B se queda esperando gates.
- Si la carpeta venía de .plans/archived/<id>/, reabierta como nueva ronda, con las tasks
  referenciando el `comment-id` que las originó.

Del entorno:
- El worktree parado en la rama del PR, y permisos de escritura acotados al repo.
- Los comandos de verificación del repo (tests/build) disponibles para correr el `verify`.

3) QUÉ PRODUCIRÍA AL TERMINAR

- Cambios en el working tree, sin commitear: el fix implementado sobre la rama del PR.
- .plans/<id>/ actualizado según la Vía B: marcas [x] en tasks.md, `status`, sección `## Verify`.
- Como mensaje final, exactamente este reporte y nada más:

    STATUS: verified | failed
    FAILURE_REASON: <1-3 líneas si failed; omitir si verified>
    AC: <una línea por AC-n: cumplido | no cumplido — evidencia breve>
    FILES: <una línea por archivo tocado>

Qué hace el conductor con eso al volver: valida `FILES` contra `git status --porcelain`, revisa el
diff con la disciplina de `receiving-code-review`, y ante `STATUS: failed` reintenta una vez con el
feedback; si vuelve a fallar, escala al usuario. Si el reporte viene ilegible el subagente no se
descarta —el artefacto es el diff, que está en el working tree—; solo se pierde la narrativa y el
conductor rearma la correspondencia leyendo el diff contra tasks.md.
